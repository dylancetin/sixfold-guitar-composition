# First-release workflow and evidence gates

This is the plan for a guitarist to arrange an existing song for solo acoustic guitar. The parent has approved reversible source, contract, test-foundation, and export-proof work after this documentation checkpoint. This design delegate writes no application code. Deployment and irreversible choices are not approved here.

The musician gets a melody-first process with audible checkpoints, a playable bass and harmony proposal, synchronized score and tab, and final PDF and MIDI. The next engineer gets one versioned musical contract and explicit adapter boundaries, rather than a renderer's data model spread through the app.

The bounded release now covers the requested song's 46 written measures and repeated performance form. An 8 to 16 measure slice is the first integration checkpoint, not a substitute song or the final release. The recommended implementation is the reused importer, an app-owned constraint-based engine, alphaTab, and real PDF bytes through PDFKit and SVG-to-PDFKit. These recommendations have probe evidence, but production adoption still needs parent approval. Estimate is 13 units and 39.5 to 60 focused hours before contingency.

## Phase A: Frame

### Scope and assumptions

The requested order is melody, then bass, then playable harmony. The brief attributes that order to a described Dominic Miller workflow. This plan uses the description as product intent, not as a verified account of his technique.

The first actual song is [The Beach Boys, You Still Believe in Me](https://www.songsterr.com/a/wsa/beach-boys-you-still-believe-in-me-tab-s692866). Arrange existing songs before adding original-song composition features. Ask for difficulty during arrangement prompting. Default the demo to intermediate with standard tuning, the user's option 1, while keeping the choice visible and changeable.

Proposed R1 arranges this one existing song on one six-string acoustic guitar. It includes one approved melody voice, a bass voice, and optional sparse harmony. It accepts the proven Songsterr source path, not arbitrary audio transcription. Track and section selection is explicit when the source is ambiguous.

The actual source has 46 written measures in 4/4, triplets, and five tempo points. Required repeat sections are bars 5 to 7 twice, 17 to 19 twice, and 43 to 46 four times. The resulting performance form has 64 measure occurrences. R1 must support that form, triplet notation and exact durations, tempo restoration on repeat jumps, rests, chords, ties, and independent sustained voices. R1 uses standard tuning with a chosen or recommended capo and compares at least capo 0 and capo 2. Preserve source rational timing and report unsupported techniques rather than silently flattening them. Other songs, arbitrary nested repeats, alternate tunings, and unsupported notation remain outside R1.

The song and demo difficulty and tuning are known. Ask for capo alongside difficulty and allow an evidence-based recommendation. B major and easier A shapes at capo 2 are user hypotheses, not established source analysis. Report the inferred source key and uncertainty before making that explanation. Capo preserves the original sounding melody and key. Transposition is a separate explicit choice. Synthetic fixture limits must not become assumed definitions of intermediate ability. Do not silently replace the requested song.

R1 excludes accounts, collaboration, payments, cloud libraries, arbitrary-song optimization, audio-to-score transcription, arbitrary website scraping, expressive performance synthesis, and a general notation editor. A melody edit form and bass or voicing alternatives are enough for R1. Beautiful acoustic synthesis is not required, but timing and voice audition are. A genuine configured LLM planner is optional. Its absence or failure must produce an honestly labeled deterministic fallback, not a claim of AI analysis.

### Release acceptance

R1 core is VERIFIED only when every gate G1 through G10 passes on the same approved arrangement revision. Any missing core gate makes the release NOT VERIFIED. An unreliable measurement is INCONCLUSIVE, never a pass. The additional LLM-assisted claim requires G11. Without provider configuration, that branch remains explicitly unverified while the constraint-based core can pass.

Usable downloads do not wait for G5. A revision passing source-identity, form, and hard physical checks can export score, PDF, and MIDI as a clearly labeled unreviewed draft. The manifest records pending musical review. Only the final playable-release claim waits for the musician. No rights or consent approval checklist is added to this product flow.

1. **G1. Source acquisition.** The supplied `s692866` URL produces actual symbolic notes through the adapted reference workflow, with source identity, retrieval date, and track mapping. A link or metadata card alone fails. Invalid, unsupported, private, unavailable, and restricted sources return explicit outcomes. An uploaded structured file does not satisfy URL ingestion by itself.
2. **G2. Melody.** The musician approves a section map, with part 1 as the intro candidate and part 0 as the main vocal candidate from bar 5. The outro needs explicit review. Source audition confirms the choice because every track's vocal flag is false. Approved pitches, onsets, durations, rests, and ties match the source across expanded form exactly. The bar-5 opening is MIDI 54, 59, 61, 63, 64, 63 with quarter durations 1, 1, 1/2, 1/2, 1/2, 1/2. Octave or key changes require explicit approval and a new revision.
3. **G3. Bass.** The app proposes bass using source parts 8 or 9 and a source-grounded, user-correctable harmonic map. Source bass reaches MIDI 28, below the guitar minimum 40, so register changes and omissions are explicit. Do not stack doubled bass parts. The musician auditions, replaces, and approves bass independently. Preserve the melody exactly and record bass octave moves and shortened sustains.
4. **G4. Harmony and physical constraints.** The final score preserves approved melody and bass. Every sounding note has a valid string and fret assignment. There are no simultaneous or sustain-overlap collisions on a string. All hard limits in the chosen ability profile pass. An unsatisfied phrase produces a useful failure or a simplification proposal, never an unlabeled impossible tab.
5. **G5. Musical review.** A guitarist reviews the complete arrangement and plays its difficult passages at the agreed target tempo. The guitarist accepts melody audibility, bass independence, useful harmony, and feasible transitions. Record the reviewer, profile, tempo, and objections. Software constraints alone do not prove musical quality or human playability. Without a guitarist, this gate stays INCONCLUSIVE.
6. **G6. Interactive playback and form.** Score, tab, audio, and MIDI share the same repeat plan and five tempo points. Verify all 64 measure occurrences, final section four times, and restored tempo at jumps. Play, pause, stop, measure seek, 50% to 125% tempo, voice mute, and a measure-range loop work. On a 60-second timing fixture, cursor error against the audio clock is at most 100 ms at sampled boundaries. Twenty loop cycles add at most 50 ms drift. Seek and stop leave no stuck notes. Record browser, device, timing method, audio-readiness failures, and an audible check.
7. **G7. PDF.** Download actual PDF bytes, not a print popup. Parse every page independently and inspect readable staff and tab, tuning, tempo, measure numbers, repeat counts, embedded music fonts, and the final bar. Raster-review first, middle, and last pages for clipping and missing glyphs at A4 and Letter sizes. Preserve complete systems across pages. Identify the revision in the manifest. A valid PDF header alone fails.
8. **G8. MIDI.** An independent parser reads the downloaded MIDI. Sounding pitches, rational onsets, durations, ties, all tempos, and expanded form match the approved event oracle exactly after documented tick conversion. It is one acoustic-guitar arrangement, not unchanged source instruments. Role-separated tracks may share the acoustic-guitar program. Tied segments produce one attack, note-on/off pairs balance, and a second MIDI player opens the file without stuck notes.
9. **G9. Revision and preference safety.** The arrangement prompt requires a difficulty choice and shows the intermediate standard-tuning demo default. Editing approved melody creates a revision and invalidates downstream approvals and exports. Editing bass invalidates harmony approval. Changing difficulty or tuning creates a revision and revalidates fingering and dependent approvals. Saving and reopening preserves events, fingering, settings, approval state, and source mapping. Errors or retries do not overwrite the last approved revision.
   The prompt also includes capo. Compare capo 0 and 2 while preserving the exact approved sounding melody and key. Preview and PDF label capo and capo-relative TAB frets. Ability or capo changes invalidate fingering and exports. MIDI must not apply the capo offset twice.
10. **G10. Reproducibility.** A clean checkout can install pinned dependencies, run validation and acceptance checks, build, and start through the documented preview lifecycle. Automated checks pass on the supported desktop browser. Keyboard operation covers import, stage approval, transport, and export. UI evidence and an independent artifact review are attached. No shipped claim depends only on an agent summary.
11. **G11. Optional configured LLM planner.** A real configured provider call returns a validated plan constrained to imported source IDs and allowed candidates. Record provider, model, plan version, accepted suggestions, and validator result. Test invalid output, timeout, missing configuration, and refusal. These paths use a visibly labeled deterministic fallback. No key means no LLM-analysis claim. A mock provider test does not prove live LLM assistance. Use the harness secret-entry workflow for credentials, never chat or committed files.

1. **Form and physical feasibility on the actual song.** The import is now proven by the research artifacts. The largest remaining risks are repeated-form identity, guitar-register bass, sustained-voice collisions, and full-song musical quality. Source access is an internal player interface, not a stable public API. Preserve blocked or restricted flags that the reference schema drops. Stop on access restrictions or 403 rather than using alternate hosts to evade denial. These are adapter behaviors, not new user approval requirements.
2. **Score, tab, and export fidelity.** The one-bar alphaTab and PDFKit probes pass parsing checks. U02 gets three focused hours to extend the tested route to independent voices, repeats, and multi-page whole-system pagination. Do not rerun a broad library comparison without a failed required gate. A screenshot without real MIDI and PDF is insufficient.
3. **Physical versus musical playability.** A fret-span rule can pass an awkward or unmusical result. Prove a solvable and impossible example early, then add human review. Do not spend an open-ended search budget hiding an unsatisfied constraint.
4. **Melody identification and harmonic ambiguity.** A multitrack source may have no isolated melody or reliable chords. Test explicit voice selection and a supplied chord map before attempting automatic inference. Audio transcription or automatic source separation requires a separate proposal.
5. **Audio and preview environment.** Browser audio requires a user gesture. Headless timing does not prove audible output. Project Shelf authentication, screenshot transfer, PDF inspection, and independent MIDI tooling need a readiness check before U11 and U12.

Each failed probe permits one corrected measurement within its timebox. A second failure or expired timebox produces a written blocker and alternatives. It does not silently expand scope.

## Phase B: Design the workflow

### Musician workflow

1. Paste a song URL. Show the supported-source result, provenance, score tracks, and any unsupported constructs. If acquisition fails, explain the reason and offer an authorized upload without pretending the URL succeeded.
2. Choose arrangement difficulty, tuning, and capo in the arrangement prompt. Show intermediate and standard tuning for the demo. Compare capo 0 and 2 and explain physical tradeoffs without silently transposing the song. Confirm the intro, vocal, and outro section map. Start with an 8 to 16 measure preview, then cover the complete song. Audition the melody alone, correct a note or range, and approve it.
3. Confirm detailed guitar constraints and the harmonic reference. Propose a sparse bass line around the locked melody. Audition both voices, edit or choose a bass alternative, and approve it.
4. Add only harmony that fits around the two approved voices. Prefer fewer notes over losing the tune or bass. Show the fingering and why a rejected option fails. Let the musician remove harmony or choose an alternative.
5. Play the complete arrangement with a cursor, tempo control, measure loop, and voice mutes. Revisit any earlier stage through explicit revision and reapproval, not hidden regeneration.
6. Review playability, save the project, and export PDF and MIDI from the exact approved revision.

### Stable domain contract proposal

The following semantics are the shared contract to approve and freeze at U03. They do not select a language, database, library, wire encoding, or implementation. Later agents consume the same versioned schema. They must not invent parallel note or timing models. Renderer-native objects remain inside adapters.

- **Project and revision.** `ProjectId`, `RevisionId`, and `schemaVersion` identify a saved arrangement. A revision contains source references, instrument and ability settings, measures, events, fingering, approvals, and diagnostics. Outputs reference a revision and a content digest. Revisions are immutable once approved.
- **Source reference.** `SourceRef` distinguishes URL import, uploaded score, and synthetic fixture. It records provider identity, original URL or safe filename, retrieved time, content digest, and parser version. Source event IDs map imports to source track, measure, voice, beat, and chord-member index. Generated notes have generated provenance. Do not store credentials or private signed URLs in exported provenance.
- **Time.** `MusicalTime` is an exact reduced rational count of quarter-note units from score start. Durations are positive rational values. Musical time is not seconds, animation frames, or floating-point milliseconds. Measures have an explicit start, meter, and length. Tempo converts musical time to seconds only at the playback boundary. Bar lines use half-open intervals to remove boundary ambiguity.
- **Form and sections.** `RepeatPlan` maps written measures to ordered `MeasureOccurrenceId` values with iteration and source identity. `TempoMap` restores effective written-position tempo at repeat jumps. `MelodySectionMap` names source part and range for intro, vocal, and outro. Occurrence IDs distinguish repeated attacks without changing source note IDs. Playback and MIDI consume the same expanded schedule. PDF may retain written repeats if its performed meaning matches that schedule.
- **Bounded unfolded projection.** A viable R1 fix materializes all 64 occurrences with explicit entry tempo and meter, removes repeat commands from the alphaTab projection, and labels original bar and pass. The literal sequence is bars 1 to 7, 5 to 7, 8 to 19, 17 to 19, 20 to 46, then 43 to 46 three more times. It totals 256 quarter notes. Use the same schedule for cursor, seek, audio, and MIDI. Do not expand and then let the renderer repeat again. Test inherited-tempo restoration separately because the actual song's marked repeat entries do not expose that bug. Define jump-boundary tie behavior explicitly.
- **Pitch and notation.** `SoundingMidiPitch` is distinct from written pitch spelling and displayed guitar octave. All physical checks and MIDI use sounding pitch. The renderer must account for octave-transposing guitar notation explicitly. No unexplained 12-semitone conversion is allowed.
- **Events.** A `NoteEvent` has stable ID, role, onset, duration, sounding pitch, notation spelling, and provenance. `RestEvent` is a separate variant. Roles are `melody`, `bass`, or `harmony`. R1 melody and bass each have at most one sounding pitch at a time. Harmony may be polyphonic. Equal pitches in separate roles remain separate events and cannot share an occupied string.
- **Ties.** A sustained sound has one identity across notation segments. Notation adapters may split it at bar lines without adding an audio attack. Muted, deleted, or omitted harmony is not encoded as a zero-duration note.
- **Guitar profile.** `InstrumentProfile` records string numbering, standard open-string MIDI pitches 40, 45, 50, 55, 59, and 64, chosen capo, and maximum physical neck fret. For TAB fret `r` relative to capo `c`, sounding MIDI equals open tuning plus `c` plus `r`. Physical neck fret equals `c` plus `r`. Physical maximum fret and relative stopped-fret stretch are independent constraints. R1 compares at least capo 0 and 2 without changing the approved sounding pitches. Capo 2 raises the minimum sounding pitch to 42 and loses low bass notes 40 and 41. Export already-sounding pitches to MIDI without adding capo again.
- **Ability and fingering.** `ArrangementPreferences` records the arrangement-time difficulty choice and instrument settings. Demo defaults are intermediate and standard tuning. `AbilityProfile` resolves that choice into explicit hard fret and finger limits separately from soft preferences such as position changes and open strings. Version that mapping and confirm it with a guitarist. `FingeringAssignment` maps each sounding note to string and fret. Its occupied interval includes the entire sustain. A chord alone passing a span test does not establish that its transition is playable.
- **Concrete held-hand schema.** `Placement` requires sound ID, string index 0 to 5 ordered low to high, fret, and finger 0 to 4. Finger 0 requires fret 0. Fretted placements require finger 1 to 4. TAB string number is 6 minus string index. `HeldContact` requires sound ID, placement ID, and exact start and release times. `HandState` requires a boundary time, active contact IDs, and hand position. Release contacts before attacks at the same timestamp. A held finger cannot move to another fret or string. Barres are unsupported in R1, not guessed from optional finger labels. Search carries these states across phrase and occurrence boundaries. Distinguish invalid candidate, exhausted search budget, and proven unsatisfiable.
- **Test profile only.** A provisional synthetic profile uses maximum physical neck fret 12, relative stopped-fret span 4, at most four sounding notes and four fretted contacts, no barre, and standard tuning. Capo-relative open strings do not increase stopped-fret span. Capo 2 therefore permits relative frets only through 10 under this physical limit. This profile is not an inferred user skill level. Transition cost thresholds require user and guitarist evidence before release.
- **Harmony reference.** `ChordMap` records user-confirmed or source-derived chord symbols, time ranges, and provenance. Unknown chords are explicit unknowns. Generated bass and harmony proposals carry their assumptions and any unresolved ambiguity.
- **Plan and changes.** `ArrangementPlan` references source candidates, density, register strategy, and explanations. Its mode is configured LLM or deterministic fallback, with provider metadata only for an actual call. `ChangeReport` records octave-revoiced bass, omissions, and shortened accompaniment sustains. A planner cannot edit the locked melody or bypass hard constraints.
- **Approval state.** Model valid stages as distinct states. `sourceReady`, `melodyApproved`, `bassApproved`, and `arrangementApproved` carry upstream revision IDs and content digests. `validatedDraft` binds passed hard checks to its digest and permits unreviewed draft downloads. Musical-review status is separate. Editing an upstream stage creates a revision and invalidates dependent approvals. If harmony cannot preserve approved bass, return a reapproval proposal, not a silent omission.
- **Outcomes.** Import and generation return explicit success, selection-needed, unsupported, permission-required, invalid-input, or unsatisfied-constraints outcomes as applicable. Diagnostics identify measure and event IDs. Neither an empty score nor a partial export counts as success.
- **Adapter boundaries.** Ingestion produces a parsed score plus diagnostics. Normalization produces domain events. Arrangement proposes a revision. An independent validator recomputes locks and physical checks. Rendering returns stable sound, segment, and occurrence mappings. A combined engraved part and role-separated playback tracks can implement voice mutes, but only one audio projection may sound. Export consumes a digest-validated draft or approved revision and returns bytes plus a status-bearing manifest.

Parse and validate untrusted data at each external boundary. If a typed language is chosen, use separate types for source IDs, event IDs, revisions, musical time, and seconds. Derive internal types from the authoritative schema where practical. These choices follow the fully read Type System Discipline leaf, not an assumed implementation of the unavailable domain-modeling skill.
